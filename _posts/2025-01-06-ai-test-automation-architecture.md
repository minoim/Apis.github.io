## 들어가며

"자연어로 작성된 테스트케이스를 AI가 자동으로 실행 가능한 코드로 변환해준다면?"

이 매력적인 아이디어로 시작한 AI 기반 테스트 자동화 프로젝트에서 겪은 시행착오와 최종적으로 도출한 아키텍처를 공유합니다. 이 글에서는 구체적인 구현 코드 대신 **설계 철학과 아키텍처 개념**에 집중합니다.

---

## 1. 초기 접근과 실패 원인

### 1.1 최초 아이디어: "완전 자동 코드 생성"

초기 접근 방식은 단순했습니다:

```
자연어 테스트케이스 → LLM → Playwright 코드 → 실행
```

AI가 테스트케이스를 읽고, 필요한 셀렉터를 찾아서, 완전한 실행 코드를 생성하는 것이 목표였습니다.

### 1.2 실패 원인 분석

그러나 실제 서비스에 적용하면서 여러 문제에 직면했습니다:

| 문제 | 설명 |
|------|------|
| **셀렉터 불안정** | DOM 구조가 복잡한 실제 서비스에서 AI의 셀렉터 추론 정확도 하락 |
| **오류 전파** | 장문 테스트케이스에서 하나의 오류가 전체 코드 생성을 망가뜨림 |
| **데이터 의존성** | 테스트 계정, 상품, 쿠폰 등 사전 데이터 미비로 매번 수작업 필요 |
| **디버깅 병목** | 생성된 코드의 문제점 파악과 수정에 과도한 시간 소요 |

### 1.3 핵심 교훈

> **"모든 코드를 AI가 한 번에 생성"하는 전략보다, 재사용 가능한 모듈을 표준화하고 AI는 모듈 조립에 집중하는 것이 현실적이다.**

---

## 2. 전환된 아키텍처: 3계층 모듈 + AI 오케스트레이션

### 2.1 핵심 철학 변경

```
Before: AI = 코드 생성기 (Code Generator)
After:  AI = 지능형 조립자 (Intelligent Assembler)
```

AI의 역할을 "코드를 직접 생성"에서 "검증된 모듈을 조립"으로 전환했습니다.

### 2.2 3계층 모듈 아키텍처

```
┌─────────────────────────────────────────────────────────┐
│                    Layer 3: 검증 모듈                    │
│         (페이지 전환 확인, 텍스트 검증, 상태 확인)         │
├─────────────────────────────────────────────────────────┤
│                    Layer 2: 기능 모듈                    │
│         (로그인, 장바구니 담기, 결제 등 비즈니스 액션)      │
├─────────────────────────────────────────────────────────┤
│                    Layer 1: 커맨드 모듈                  │
│            (click, fill, wait 등 저수준 동작)            │
└─────────────────────────────────────────────────────────┘
```

#### 각 계층의 역할

| 계층 | 역할 | 예시 |
|------|------|------|
| **커맨드** | UI 저수준 동작 래핑 | 클릭, 입력, 대기 |
| **기능** | 비즈니스 의도 단위 | 로그인, 상품 검색, 주문 |
| **검증** | 결과 확인 표준화 | 알림 확인, 페이지 이동 확인 |

### 2.3 변환 흐름

```
자연어 TC
    ↓
┌─────────────────────────────────────┐
│        AI 오케스트레이터             │
│  "로그인 모듈 실행" → 기존 모듈 호출   │
│  "버튼 클릭" → 단순 코드 생성         │
└─────────────────────────────────────┘
    ↓
모듈 조합 실행
```

## 3. Page-Centric Package 구조

### 3.1 왜 페이지 중심인가?

기존의 분리 구조에서는 셀렉터, 모듈, 테스트케이스가 각각 다른 폴더에 있어서:

- 변경 시 3곳을 오가며 수정
- 연관 파일 찾기 어려움
- 페이지 단위 독립 테스트 불가

### 3.2 통합 구조

```
페이지별 패키지/
├── POM/           # 셀렉터 정의 (어디에 있는가)
├── modules/       # 동작 구현 (어떻게 동작하는가)
│   ├── action/    # 액션 모듈
│   ├── checks/    # 검증 모듈
│   └── commands/  # 커맨드 모듈
└── testcase/      # 테스트 시나리오 (무엇을 하는가)
```

### 3.3 장점

- **높은 응집도**: 페이지 관련 모든 것이 한 곳에
- **명확한 계층**: POM → 모듈 → 테스트케이스 (상향식)
- **독립 테스트**: 페이지 단위로 실행 가능
- **쉬운 탐색**: IDE에서 즉시 이동 가능

## 4. 3-Layer 동적 셀렉터 아키텍처

동적으로 변하는 UI 요소(예: 상품 옵션)를 처리하기 위한 계층 분리 원칙입니다.

### 4.1 구조

```
┌─────────────────────────────────────────────────────────┐
│  Data Contract     "무엇이 있는가"                       │
│  (데이터 계약)      옵션 구조와 값 정의                   │
└──────────────────────┬──────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────┐
│  POM                "어디에 있는가"                       │
│  (Page Object)      템플릿 셀렉터 정의                    │
└──────────────────────┬──────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────┐
│  Module             "어떻게 실행하는가"                   │
│  (모듈)             변수 해석 및 실행                     │
└─────────────────────────────────────────────────────────┘
```

### 4.2 각 레이어의 책임

| Layer | 책임 | 내용 |
|-------|------|------|
| **Data Contract** | 데이터 정의 | 테스트에 사용할 데이터의 구조와 값 |
| **POM** | 위치 정의 | UI 요소를 찾기 위한 템플릿 셀렉터 |
| **Module** | 실행 로직 | 변수를 해석하고 실제 동작 수행 |

---

## 5. Data Contract: 테스트 데이터 일관성의 핵심

### 5.1 문제 상황

```
페이지 A: 상품을 장바구니에 담음
페이지 B: 장바구니에서 가격 확인

→ 두 페이지에서 사용하는 "상품"이 같다는 보장이 없음
```

### 5.2 해결책: 표준 데이터 계약

테스트 전체에서 사용할 데이터를 **계약(Contract)**으로 정의합니다:

```
데이터 계약의 구성:
├── guaranteed_fields   # 보장되는 필드값
├── expected_behaviors  # 예상되는 결과값
└── required_settings   # 필요한 사전 설정
```

### 5.3 효과

- 모든 페이지 테스트가 **동일한 데이터** 사용
- 예상 결과값이 **명확하게 정의됨**
- 페이지 간 데이터 **일관성 보장**

## 6. 2-Layer Feature 구조

### 6.1 왜 2계층인가?

하나의 큰 E2E Feature로 모든 시나리오를 작성하면:

- AI 오케스트레이터의 모듈 매칭 정확도 하락
- 유지보수 시 수정 범위 파악 어려움
- 특정 페이지만 테스트 불가능
- 코드 중복 불가피

### 6.2 구조

```
┌─────────────────────────────────────┐
│  페이지별 Feature (Atomic)           │
│  - 단일 페이지 내 독립적 기능          │
│  - 레고 블록처럼 재사용 가능           │
└──────────────────┬──────────────────┘
                   ↓ 조합
┌─────────────────────────────────────┐
│  통합 시나리오 Feature (Chained)     │
│  - 여러 페이지를 거치는 E2E 시나리오   │
│  - 페이지별 Feature를 조합하여 구성    │
└─────────────────────────────────────┘
```

### 6.3 실행 전략

| 구분 | 비율 | 용도 |
|------|------|------|
| **동적 조립** | 90% | 탐색적 테스트, 빠른 프로토타이핑 |
| **정적 Feature** | 10% | 핵심 회귀 테스트, CI/CD 자동화 |

## 7. Feature Step의 철학

### 7.1 "파라미터화된 사용자 의도의 선언"

Feature의 각 Step은 **절차도 순수 명세도 아닌** 그 사이의 Sweet Spot입니다:

```
순수 명세 ────── 실행 가능한 명세 ────── 순수 절차
(실행 불가)      (권장)              (구현 의존)
```

### 7.2 예시

| 유형 | 예시 | 문제점 |
|------|------|--------|
| 순수 명세 | "옵션을 선택할 수 있다" | 실행 불가 |
| **실행 가능한 명세** | "색상 옵션에서 블랙을 선택한다" | **권장** |
| 순수 절차 | "색상 드롭다운을 클릭한다" | UI 변경 시 깨짐 |

### 7.3 핵심 원칙

- **의도 중심**: "무엇을" 하려는지 선언
- **구현 독립**: "어떻게" 하는지는 숨김
- **도메인 언어**: 비즈니스 용어 사용

## 8. 실행 아키텍처

### 8.1 전체 흐름

```
통합 시나리오 (동적 조립 or 정적 Feature)
                ↓
        실행 엔진 (Runner)
        - Feature 블록 리스트 수신
        - Context 초기화 (표준 데이터 로드)
                ↓
        AI 오케스트레이터
        - Step → Module 매칭
        - Context 공유 및 업데이트
                ↓
        모듈 실행 (Action/Check/Command)
                ↓
        브라우저 자동화 (Playwright 등)
```

### 8.2 핵심 원칙

- **명시적 블록 참조**로 실행 순서 명확
- **Context 공유**로 페이지 간 데이터 전달
- **모듈 조합**으로 유연한 시나리오 구성

## 9. 결론: 배운 점

### 9.1 핵심 교훈

1. **AI의 역할 재정의**: 코드 생성기 → 지능형 조립자
2. **모듈화의 중요성**: 재사용 가능한 검증된 모듈 표준화
3. **데이터 일관성**: Data Contract로 테스트 데이터 계약
4. **계층 분리**: 각 계층의 책임을 명확히 분리

### 9.2 아키텍처 선택의 이유

| 특성 | Before | After |
|------|--------|-------|
| AI 역할 | 전체 코드 생성 | 모듈 조립 |
| 재사용성 | 낮음 | 높음 |
| 유지보수 | 어려움 | 용이 |
| 안정성 | 불안정 | 안정적 |
| 디버깅 | 병목 발생 | 분산 가능 |

### 9.3 마무리

AI 기반 테스트 자동화는 "마법"이 아닙니다. 체계적인 아키텍처 설계와 적절한 역할 분담이 있어야 실제 서비스에서 동작하는 시스템을 만들 수 있습니다.

실패를 통해 배운 것들이 결국 더 나은 설계로 이어졌습니다.
